## ID-001 — KB 통합 0% 정량적 확정

이번 세션의 가장 큰 산출물.

### 결정적 증거 chain

1. **KB note 가 semantic 인덱스에 등록 안 됨** (s10 + s15 확인):
   - `knowledge_aggregator.upsert` → `KnowledgeStore.ApplyPatch` → 마크다운 파일 작성 + `rebuildArtifacts` (index.md + graph.json)
   - **`semantic.IndexEntry`/`IndexExperience` 호출 없음**
   - 즉 `backend.Search` 결과에 KB 0%

2. **`memory_search.include_knowledge` 기본 false** (s15):
   - description 자체가 자백: *"Search knowledge-base notes only when explicitly requested."*

3. **`prompt/memory_retrieval.go` 의 fallback chain 에 KB 매처 없음** (s11):
   - 6 매처: project(dead) + brief(dead) + experience + memory_file + daily + session

→ **chat path 에서 LLM 이 KB 사용하려면 두 단계 명시 필요**:
- (1) `memory.search` action 호출
- (2) `{ include_knowledge: true }` 명시

LLM 이 자발적으로 두 단계 모두 충족할 확률 매우 낮음. **실질 통합 0%** 확정.

### 역방향 비대칭 (s15 발견)

- **KB**: read 닫힘 (chat 통합 0%) / write 열림 (`knowledge.upsert` 가능)
- **MEMORY.md**: read 가능 (memory_get + memory_search) / **write 자동 열림** (`memory_save` 의 AppendMemoryNote — RF-036)

→ memory 표면의 통합 정책이 일관되지 않음. 두 곳 모두 **사용자 의도 vs LLM 의도 경계 흐림**.

### ID-001 결정 부담 가중

가설 A ("read side 미완성") **확정 강화**. 행동 갈래 4개 (1) 유지 (2) 단순화 (~1.4k LOC 감소) (3) 활용 확장 (4) 부분 정리. **(2) 의 정당성 가장 강함** — read 통합이 없는 기능은 사실상 휴면.

## ID-003 — `process` schema 패턴이 file/web 통합의 모범

### Aggregator schema 패턴 정량 비교

| Aggregator | properties | additionalProperties | LLM 정확도 |
|-----------|-----------|---------------------|----------|
| `memory` | action만 | true | ⚠️ 낮음 |
| `knowledge` | action만 | true | ⚠️ 낮음 |
| `workspace` | action만 | true | ⚠️ 낮음 |
| `automation` | action + 일부 | mixed | 중 |
| `session` | action + 일부 | mixed | 중 |
| **`process`** | action + session_id + chars (전체) | false | ✅ 높음 |

→ **`memory`/`knowledge`/`workspace` 는 partial schema** — LLM 이 sub-action params 추측. strict tool calling 에서 schema validation 약함.

→ **`process` 패턴 = 모든 sub-action param top-level + action enum 분기 + additionalProperties=false**. schema 살짝 두꺼워지지만 LLM 호출 정확도 ↑.

### file/web aggregator 만들 때 적용

ID-003 본문에 `process` 패턴 schema 예시 추가. file aggregator 의 schema 가 ~600B (현 6 분리 툴 ~1.2KB 의 50% 감소) — LLM 정확도 입증된 패턴.

### 추가 권고

기존 `memory`/`knowledge`/`workspace` 의 partial schema 도 `process` 패턴으로 마이그레이션 가치 있음. 별도 RF 분리 가능 — 다만 현재 LLM 호출이 *경험적으로 잘 됨* 일 수 있어 우선순위 낮음.

## 핵심 인사이트

### 좋은 패턴 ⭐

- **memory aggregator description 의 라우팅 hint** — *"For user profile info, use workspace tool instead."* 다른 aggregator 로의 명시적 안내. LLM 의 잘못된 저장 위치 방지.
- **Score 시스템 통합** — 4 source × 4 boost (knowledge +120, memory +100, experiences +80, sessions +80) — 의도된 우선순위
- **dedup by source|snippet|line** — 같은 매치 중복 방지

### 약한 부분

- **Partial schema aggregator** [ID-003 보강] — memory/knowledge/workspace 의 sub-action params 가 schema 외 (additionalProperties: true)
- **MEMORY.md 자동 append** [RF-036] — 사용자 영역 경계 침범
- **fallback chain 중복** [RF-037] — tool 과 prompt 두 곳에 거의 같은 코드
- **description 자기모순** [RF-038] — include_sessions

### 결정 인풋 모임

- **ID-001**: 가설 A 확정 강화 — KB read 통합 0% 의 결정적 증거 chain 완성
- **ID-003**: file/web aggregator schema 작성 시 `process` 패턴 권장 (모든 sub-param top-level + action enum). 기존 partial schema aggregator 보강도 가능
