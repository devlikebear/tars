# Session 13 — `internal/tool/` file ops + 통합 가능성 평가

이번 세션부터 사용자가 추가 분석 관점을 명시:

> "현재 빌트인 툴이 너무 많은데, 꼭 필요한지 여부와 툴을 단일로 통합할 수 있을지(read_file & write_file -> file 등), 통합이 더 효율적일지(LLM입장에서 사용하기에) 분석도 같이 진행해줘"

→ 이 관점이 [ID-003](../findings/ideas.md#id-003)으로 산출. 이번 세션의 가장 큰 부산물.

## 패키지 한눈에

### 좋은 패턴

1. **PathPolicy 추상화** (`workspace_path.go`):
   - `PrimaryDir` (relative path resolution base) + `AllowedDirs` (모든 접근 허용 디렉토리)
   - `SingleDirPolicy` (legacy compat) + `NewPathPolicy` (workspace + workDirs + currentDir)
   - 읽기/쓰기 경로 분리: `resolvePathWithPolicy` (read) vs `resolveWritePathWithPolicy` (write — 존재하지 않는 path도 OK, 부모까지 escape 검증)
   - **symlink escape 검증** — 모든 read/write가 symlink 해석 후 다시 boundary 체크

2. **read_file 의 line-oriented pagination**:
   - default 2000 lines, max 2000 — 큰 파일 안전 처리
   - `truncateReadLines` (라인당 max 2000자), `Truncated` flag, `NextOffset` 안내
   - **`secrets.RedactText`** — 출력에 자격 증명 자동 redaction
   - `buildReadFileMessage` 가 truncation 종류별 명확한 안내 (LLM이 다음 호출 결정)

3. **write_file 의 atomic write**:
   - tmp file create → chmod → write → sync → close → rename
   - Windows fallback (rename 실패 시 remove + retry)
   - 권한 보존 (`info.Mode().Perm()`)

4. **edit_file 의 strict replace**:
   - 매칭 0건 → 에러
   - 다중 매칭 + `replace_all=false` → 에러 (실수 방지)
   - 명시적으로 `replace_all=true` 줘야 다중 치환

5. **apply_patch 의 다층 가드**:
   - `enabled` flag
   - `maxApplyPatchFiles` (20)
   - 절대 경로 거부, `..` escape 거부
   - parsePatchFiles로 사전 검증

6. **glob 의 workspace boundary**:
   - 절대 경로 + `..` 거부
   - matches 결과를 `policy.AllowedDirs` 안에서만 필터

## 새 분석 관점 적용 — "필요한가/유용한가" + "통합 가능성"

**시스템 프롬프트 비용 정량화** (rough):

- 6 file 툴 description + parameter schema → ~1.5-2KB → ~400-500 토큰
- 6 default-non-file 툴 → ~1-1.5KB → ~250-400 토큰
- → **default ~750-900 토큰/turn 베이스 비용**
- + optional/caller-added → 1500-2000 토큰/turn 가능

매 chat turn마다 ↑ 비용 — 누적.

### 통합 관점 평가 — file aggregator 시나리오

분석은 [ID-003](../findings/ideas.md#id-003) 본문으로. 핵심 요약:

| 측면 | 6 분리 툴 | 1 file aggregator | 차이 |
|------|----------|-------------------|------|
| Description 합 | ~298자 | ~150자 | -50% |
| Parameter schema | ~1.2KB | ~1.5KB (oneOf 비용) | +25% |
| 시스템 프롬프트 토큰 | ~400 | ~250 | -150 토큰/turn |
| LLM 정확도 | 단순 schema에 강함 | CRUD 패턴에 강함 | 케이스별 |

**file 도메인은 통합 후보로 자연스러움**:
- 모두 같은 PathPolicy 공유
- 모두 같은 backend (filesystem)
- read/write/edit/list/glob 의 도메인 일관성
- 기존 aggregator 6개 (memory/knowledge/workspace/automation/session/subagents_*) 의 정당성 패턴 재사용

**의문점**:
- LLM이 schema 단순한 multi tool을 더 정확히 사용한다는 경험적 판단이 코드베이스에 있을 수 있음 (file/exec/web만 분리 유지)
- aggregator의 oneOf schema 복잡도 — strict tool calling에서 LLM 거부율 ↑ 가능

## 새 발견 (RF급)

### RF-019 보강 (Go built-in 사용)
- `list_dir.go:172-177` 의 자체 `minInt(a, b int)` 추가. semantic.go + builder.go 와 함께 6건 일괄 정리.

### RF-029 — read_file의 6 parameter 중복

`offset`+`limit` (canonical) + `start_line`+`end_line` (Gemini-style) + `max_bytes` (legacy) + `path`. 5개가 같은 의미를 다른 이름으로. `resolveReadLineWindow` 가 셋 다 처리. **LLM에게 혼란**. canonical 1쌍으로 단순화 권장.

### RF-030 — File 툴 등록 시그니처 3중

`NewReadTool(workspaceDir)` / `NewReadFileTool(workspaceDir)` / `NewReadFileToolWithPolicy(policy)` — 5개 file 툴 모두 동일 패턴. 실제 등록은 `WithPolicy` 만. 단순화 가능.

## 핵심 인사이트

### 좋은 패턴 (file ops 영역)

- **PathPolicy 추상화** — 읽기/쓰기 분리, symlink escape 검증, multi-dir support
- **secrets.RedactText 통합** — read_file 결과에 자동 적용 (보안)
- **atomic write + Windows fallback** — 안전한 write 전 코드베이스 표준
- **edit_file 의 strict replace** — 다중 매칭은 explicit consent 필요 (실수 방지)
- **buildReadFileMessage** — LLM이 다음 호출 결정에 필요한 정보 명시 (start_line, NextOffset)

### 약한 부분

- **parameter alias 분산** [RF-029] — Gemini-style + canonical + legacy 셋 다 받음
- **시그니처 3중** [RF-030] — 5 file 툴 모두 동일 패턴 반복
- **자체 minInt** [RF-019 보강] — Go built-in 쓰면 됨
- **통합 정책 부재** [ID-003] — 새 사용자 요청의 핵심
