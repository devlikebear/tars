## 한 줄 요약

Knowledge 시스템은 *Wikipedia-style 노트 + 그래프*인데 — **write side는 존재하지만 read side(특히 그래프 시각화 + chat 통합)가 미완성**. 정말 필요한지/유용한지에 대해 [ID-001](../findings/ideas.md#id-001)로 결정 보류.

## 흐름 요약

### 1단계 — 타입과 스토어

**`knowledge.go` 타입 가족 (L17-77)**:

- `KnowledgeNote` — slug + title + kind + summary + body + tags + aliases + **links** (slug 참조)
- `KnowledgeNotePatch` — partial update (각 필드 *T 포인터)
- `KnowledgeGraphNode/Edge/Graph` — 노트→nodes, links→edges
- `KnowledgeUpdate` — `{notes, edges}` 배치 (nightly LLM이 만드는 JSON 페이로드)

각 타입에 `MarshalJSON/UnmarshalJSON` 페어 — `time.Time`을 빈 문자열 vs RFC3339로 안전하게 처리. (**참고**: 이 안전장치 자체가 `Graph()` 의 자가치유 로직 [RF-022]를 부른 원인.)

**`KnowledgeStore` (L226-240)**: stateless. 필드는 `root` (string), `semantic` (*Service), `nowFn`. 내부 검토:

- `FileBackend.knowledgeStore()` 가 매번 `NewKnowledgeStore` 호출 (file_backend.go:95-96).
- → "stateful이면 문제" 의문(s09)은 답: stateless 확정. 매번 new 비용은 미미.
- 단, **`nowFn` 필드는 외부 주입 경로 없음** (NewKnowledgeStore 시그니처에 옵션 없음, exported 필드 아님). 테스트에서도 활용 안 함. → [RF-020] dead capability.

### 3단계 — KnowledgeStore API 면밀 분석

**`Upsert` (L242-275)** — `KnowledgeNote` 를 받아 `KnowledgeNotePatch` 로 변환 + `ApplyPatch`. trim/normalize 후 빈 필드는 patch에 포함 X (partial semantics 보존).

**`ApplyPatch` (L277-351)** — 핵심 로직:

1. slug 정규화 (`normalizeKnowledgeSlug`)
2. 기존 노트 read (`Get`) — 없으면 빈 노트 시작
3. patch의 *T 필드만 덮어쓰기 (nil은 보존)
4. 기본값 채움 (Title=titleFromSlug(Slug), Kind="note")
5. **마크다운 파일 작성** (`buildKnowledgeDocument` → frontmatter + sections)
6. **`rebuildArtifacts()` 호출** ← 매 upsert!

`rebuildArtifacts` (L521-538):
- `List({Limit: 10000})` → 모든 `*.md` glob + 파싱 + filter sort
- `index.md` 전체 재작성 + `graph.json` 전체 재작성

→ **N개 노트 upsert 시 N×N 비용** [RF-021]. ApplyUpdate (nightly compileKnowledge) 가 N개 note를 처리할 때마다 매번 전체 재빌드.

**`ApplyUpdate` (L353-389)** — nightly compileKnowledge가 호출하는 배치:

```go
for _, note := range update.Notes {
    saved, err := s.Upsert(note)  // ← 매번 rebuildArtifacts
    ...
}
for _, edge := range update.Edges {
    note, _ := s.Get(source)
    links := append(...)
    s.ApplyPatch(...)  // ← 또 rebuildArtifacts
}
```

**`Get/List/Delete` (L391-472)** — 익숙한 file IO. List가 모든 `.md` 글로브 + 매번 파싱 + sort by UpdatedAt. defaultLimit=200.

**`Graph()` (L474-515)** — 자가치유 로직 3단계:

1. graph.json 누락 → rebuildArtifacts
2. JSON unmarshal 실패 → rebuildArtifacts
3. **`"updated_at": ""` substring 발견** → rebuildArtifacts (옛 포맷 마이그레이션)

→ 3번이 magic. 한 번 정상화되면 transient한 케이스에 매 호출마다 substring scan. [RF-022] 단순화.

### 4단계 — buildKnowledgeIndex/Graph 디테일

`buildKnowledgeGraph` (L540-586): notes → nodes (sorted by slug). links → edges (dedup with `{source}|{target}|{relation}` key, sorted). `updatedAt`은 max over notes.

`buildKnowledgeIndex` (L588-626): kind별 그루핑 → markdown bullet 리스트 with `[[slug]] title — summary`. 카운트(노트 수, relations 수) 헤더.

`buildKnowledgeDocument` (L628-673): YAML frontmatter + `# Title` + `## Summary` / `## Details` / `## Links`. wiki-style.

`parseKnowledgeDocument` (L675-705) + `splitKnowledgeFrontmatter` (L707-720): frontmatter `---\n...\n---\n` 분리. unterminated 케이스 에러.

`normalizeKnowledgeSlug` (L756-780): lower + a-z0-9만 보존, 그 외는 `-`, 끝 `-` trim. 한글/유니코드 글자는 모두 dash로 처리됨 → KR slug는 `-` 만 남는 결함 있음 (e.g. "한글 제목" → ""). 하지만 `Upsert`가 빈 slug면 title fallback이 있어 곧바로 깨지진 않음. 발견은 했지만 finding 등록은 보류 — KR slug 정책 결정이 사용자 수준 질문이라 ID-001 본문에 포함.

### 5단계 — 새 분석 관점 적용 ("필요한가/유용한가")

이번 세션부터 도입한 관점. knowledge.go에 적용한 결과 → [ID-001](../findings/ideas.md#id-001).

**비활용 신호 4개**:

1. **`memory_search` 기본 `include_knowledge=false`** + 도구 description 자체가 *"only when explicitly requested"* — chat 시 LLM이 KB를 자발적으로 검색 안 함.

2. **`shouldCompileKnowledge` 게이트가 14개 키워드** — nightly trigger 빈도가 낮음. compileKnowledge가 turn 단위로 호출되지만 hint 매칭 없으면 0건.

3. **콘솔 UI의 그래프 시각화 부재** — `KnowledgeGraph` import + fetch는 있지만 렌더링은 *`{graph.edges.length} KB relations`* 카운트뿐. 그래프 시각화 컴포넌트 X.

4. **빌트인 툴 비용** — `knowledge` aggregator 의 description이 매 chat turn 시스템 프롬프트에 박힘 (KB가 비어 있어도). CLAUDE.md *"Every tool ... emits its description into the chat system prompt"* 비용 그대로.

→ Knowledge feature는 야심찬 wiki-style memory의 *write 경로*는 잘 구현됐지만, *read 경로 통합* 이 절반 이상 비활성. write only 의 위험.

**4가지 행동 갈래** (사용자 결정 필요):

- (1) 현 상태 유지
- (2) 단순화 — KnowledgeNote 제거, Experience + MEMORY.md만 (~1.4k LOC 감소 가능)
- (3) 활용 확장 — `include_knowledge` 기본 true + 그래프 시각화 + 게이트 확대
- (4) 부분 정리 — 그래프 부분만 제거, wiki 노트는 유지

정량 데이터 수집 후 결정 추천 (사용자 본인의 KB 활용 빈도 회고).

## 핵심 인사이트

### 좋은 패턴

- **Frontmatter + sections markdown 노트** — 사람이 직접 편집하기 좋고 LLM이 생성하기 좋은 포맷
- **dedup key in graph build** — `{source}|{target}|{relation}` 으로 중복 edge 제거
- **MarshalJSON/UnmarshalJSON 페어** — 빈 시간을 빈 문자열로 안전하게 처리
- **partial patch semantics** — `*T` 포인터로 nil은 "변경 안 함"

### 미세한 약점

- **`normalizeKnowledgeSlug` 의 KR 무시** — 한글이 모두 dash 처리됨. ASCII slug 정책이 의도된 거면 명시 필요. (ID-001 본문에 포함)
- **`Graph()` 의 magic substring 검사** — 옛 포맷 transient 처리가 hot path에 박힘 [RF-022]
- **`rebuildArtifacts` 의 N×N batch 비용** — 노트 수 늘면 nightly가 무거워짐 [RF-021]

### 관점 추가의 효과

새 관점("필요한가/유용한가")이 도입된 첫 세션. 결과:

- 코드 리뷰 단독으로는 발견하지 못했을 **활용 측면 미완성**을 ID-001로 명시
- "단순화 vs 확장" 결정이 RF가 아니라 **사용자 결정**임이 명확해짐 (ID 카테고리 정당)
- nightly cost / 시스템 프롬프트 비용 / 콘솔 UX gap 같은 *교차-패키지 문제*가 한 finding에 모임 → 결정 효율 ↑

이 관점은 다음 세션부터도 계속 적용. 특히 `tool/` 검토 시 큰 효과 예상.
