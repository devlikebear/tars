## 좋은 패턴 ⭐⭐ (다수 누적)

### 1. path-level mutex via sync.Map (locks.go)

```go
var pathLocks sync.Map
func lockPath(path string) func() {
    value, _ := pathLocks.LoadOrStore(path, &sync.Mutex{})
    mu := value.(*sync.Mutex)
    mu.Lock()
    return mu.Unlock
}
```

→ 각 file path 마다 **자동 생성 mutex**. 동일 path 동시 write 직렬화. `defer unlock()` 패턴. **모범**.

→ **사용자 facing 핵심 데이터** 인데 atomic write 미적용. **공통 헬퍼** (`internal/atomicwrite/`) 추출 후 session/gateway/knowledge 모두 사용.

## 핵심 인사이트 — chat session 인프라의 정교함

### 다층 token 관리

1. **Message-level** — `messageTokenCost` (CJK 가중치)
2. **History-level** — `LoadHistorySnapshot` token budget backwards walk
3. **Compaction-level** — 3 전략 (fraction/tokens/count)
4. **Compaction summary 보존** — token budget 잘라도 boundary 유지

→ **chat 컨텍스트 관리의 4-layer**. CLAUDE.md *"context window management"* 의 본거지.

### Compaction 의 결정적 요소

- LLM-based summary (caller 가 SummaryBuilder 제공) + fallback heuristic
- Stacking carry-forward (이전 summary 영원히 보존)
- pruneToolResults (코드 dump 방지)
- 5 sections (Topic/Key Decisions/Active Identifiers/Current State/Prior Context)
- 한국어 + 영어 키워드 매칭

→ **체계적 + 다국어 지원**. 단순 *"마지막 N개 메시지"* 가 아닌 의미 기반 압축.

session 수가 100+ 가는 워크스페이스에서 매 mutation 의 O(N) 비용 누적. RF-017/021 와 같은 카테고리. **3 사례 누적** = 코드베이스 안티패턴 — SQLite 등 큰 결정 시점.

## 세션 수 추정 + 큰 결정 시점 평가

- chat session 100 = 매일 1 session × 100일 (3개월)

→ 일반 사용자도 수개월 내 100+ 도달 가능. RF-058 우선순위 ↑.
