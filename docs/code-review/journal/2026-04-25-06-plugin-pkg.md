## 흐름 요약

### 1. 인터페이스 + Registry (builtin.go + builtin_registry.go, 합 57줄)

`BuiltinPlugin` 6 메서드: `ID`, `Definition`, `Init(PluginContext)`, `Tools`, `HTTPHandlers`, `Close`. `PluginContext`는 `Config map[string]any` + `WorkspaceDir`. Registry는 단순 슬라이스 + RWMutex + defensive copy.

### 2. types.go (110줄) — 스키마

5 핵심 타입: `Manifest` (디스크) → `Definition` (런타임) → `Snapshot` (로드 결과). `Source` enum 3계층 (workspace/user/bundled). `AvailabilityOptions`는 OS/Arch + HasEnv/HasCommand 함수 주입.

**핵심 발견 1**: `Manifest`와 `Definition`이 12개 공통 필드를 각자 정의 → embed로 단순화 가능. → [RF-011](../findings/refactor.md#rf-011).

**코멘트가 자백한 두 가지** (이미 등록):
- `ToolsProvider.Type` 코멘트의 "script" 명시 vs 미구현 → TN-003 재확인.
- `Lifecycle` 코멘트의 "shell commands" 명시 → RF-008은 단순 버그가 아니라 **설계 변경**.

**RF-008 보강 발견**: `Manifest.MCPServers []config.MCPServer` — 플러그인이 자체 MCP 서버 declare 가능. RF-008 위협 모델에 추가 위협 표면으로 보강.

### 3. manifest.go (117줄) — 파싱 + 검증 + 정규화

`parseManifestFile(path)` — JSON unmarshal → trim → SchemaVersion 검증 (1-3) → v3 전용 필드 가드 → normalize. 코드 품질 좋음, 새 finding 없음.

좋은 패턴:
- v3 전용 필드를 v1/v2 매니페스트에 못 쓰게 강제 (forward-compat 차단)
- 친절한 에러 메시지 (`tools_provider requires schema_version >= 3`)
- `SchemaVersion=0` → v2 default (보수적)

### 4. loader.go (335줄) — 디스크 로딩

**`Load(opts)`** (L18-49):
1. 각 source `loadSourcePlugins`로 로드
2. ID로 merge (단순 덮어쓰기 — 마지막이 이김)
3. 정렬 + availability 필터
4. skill/MCP 수집

**핵심 발견 2**: Source 우선순위가 호출자 슬라이스 순서에 100% 의존 → [Q-008](../findings/questions.md#q-008) → resolved → [RF-013](../findings/refactor.md#rf-013) 승격.

**`loadSourcePlugins`** (L51-129) — 가장 큰 함수. `filepath.WalkDir`로 manifest 탐색. 같은 ID 중복 시 `manifestPriority` 적용. **Manifest → Definition 매핑 86줄 boilerplate** (L87-109) — RF-011 적용 시 ~5줄로 축소되는 가장 큰 수혜처.

**`manifestPriority`** + `manifestFilename`/`legacyManifestFilename` — `tars.plugin.json`(우선) vs `tarsncase.plugin.json`(legacy). "tarsncase"는 단순 잔재가 아니라 옛 프로젝트 이름 → [RF-012](../findings/refactor.md#rf-012) (단계적 deprecation).

**`collectSkillDirs`** (L131-183) — **좋은 보안 패턴**:
- 절대 경로 금지
- `pathWithin(absPath, rootAbs)` 로 path traversal 방지
- 디렉토리 존재/타입 검증

→ RF-009(외부 플러그인 HTTP) 결정 시 같은 패턴(namespace + path 검증)으로 가는 게 자연스러움.

**`collectMCPServers`** (L185-203) — RF-008 보강 위협의 정확한 코드 위치. 보안 게이트 없음.

**`filterUnavailablePlugins`** + `availabilityChecker` (L205-280) — runtime defaults + 함수 주입. 깔끔.

### 5. helpers_build_extensions.go (Q-008 해소)

`buildPluginSources` 의 호출 순서:

```
[0] SourceBundled    cfg.PluginsBundledDir
[1] SourceUser       ~/.tarsncase/plugins        ← legacy
[2] SourceUser       ~/.tars/plugins
[3] SourceUser       cfg.PluginsExtraDirs
[4] SourceWorkspace  cfg.WorkspaceDir/plugins
```

마지막이 이기는 머지 → **결과 우선순위: workspace > user(extra) > user(.tars) > user(.tarsncase) > bundled**. 합리적, 마이그레이션 안전.

`buildSkillSources`도 동일 패턴.
